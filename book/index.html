작은 작품을정성껏 만들기

이 책을 Terry A. Davis에게 바칩니다.

테리는 컴퓨터 안에 신을 위한 성전을 만들고자 했습니다. 그에게 프로그래밍은 결과물을 얻기 위한 기술이면서, 아름다움을 만들고 바치는 일이었습니다. 그의 헌장은 성전의 장식과 아이들이 만드는 그림, 소스의 공개와 단순한 구조를 같은 이야기 안에 놓습니다.

우리는 그 뜻을 다음과 같이 실천합니다. 읽을 수 있을 만큼 작은 프로그램을 만들고, 만든 사람이 원리를 이해하며, 다른 사람이 고쳐 볼 수 있도록 코드를 함께 둡니다. 책의 끝에서는 일곱 개의 등불을 켜는 작은 작품을 완성합니다.

한 줄을 읽고, 한 가지를 바꾸고, 결과를 바라봅니다. 서두르지 않아도 됩니다. 오늘 이해한 한 줄이 내일의 작품을 지탱합니다.

작은 프로그램을 정성껏 만드는 일이 우리의 봉헌이 되기를.

이 문장은 이 책의 헌정문입니다.

컴퓨터를 켜고 파일을 저장해 본 적이 있으면 시작할 수 있습니다. C 언어를 미리 알 필요는 없습니다. 다만 새 언어와 오래된 운영체제의 사용법을 함께 배우므로, 첫날에는 첫 인사말을 출력하는 데 집중하세요.

각 강의는 알기 → 그대로 실행하기 → 한 곳 바꾸기 → 설명하기로 이어집니다. 코드를 한 번에 외우지 않습니다. 화면에 무엇이 나올지 먼저 예상하고, 실제 결과와 비교하는 습관을 기릅니다.

책의 설명은 한국어, TempleOS 안에서 입력하는 코드·파일명·문자열은 ASCII 영문입니다. 원본 TempleOS는 한글과 Unicode를 기본 지원하지 않습니다. 한글 설명을 코드 안으로 그대로 옮기면 글자가 깨질 수 있습니다.

코드 머리말의 파일명과 같은 이름으로 저장하세요. HELLO.HC처럼 대문자 영문과 짧은 이름을 사용합니다. PDF에서 복사한 내용은 따옴표와 역슬래시를 확인하고, 가능하면 함께 제공한 원본 파일을 이용합니다.

한 강의의 완료 기준은 실행 성공과 설명입니다. 예를 들어 반복문을 배운 뒤에는 “몇 번 반복했고 왜 멈췄는지”를 말할 수 있어야 합니다. 그래픽 강의에서는 한 좌표를 바꾸고 그림이 이동한 이유를 설명합니다.

이 책은 원본 TempleOS 5.03을 기준으로 합니다. 후속 운영체제에는 이름과 API가 달라진 곳이 있으므로 원본 실습과 섞지 않습니다.

01 · 뜻을 읽다

테리가 만들고자했던 것

TempleOS의 헌장인 Doc/Charter.DD는 성전이 마음을 모으는 장소이며, 아름다운 것을 만들어 바치는 공간이라고 설명합니다. 테리는 그 생각을 운영체제와 연결했습니다. 아이가 그림을 만들고, 사용자가 코드를 읽고, 창작물을 나눌 수 있는 컴퓨터를 원했습니다.

그는 640×480의 해상도와 16색을 고정된 약속으로 서술했습니다. 화면의 제약을 직접 이해할 수 있는 작업 조건으로 받아들인 것입니다. 그래픽 계산을 외부 GPU에 숨기지 않고, 운영체제 안에서 살펴볼 수 있게 하려 했습니다.

또 하나의 핵심은 사용자가 개발자라는 관점입니다. 명령을 입력하는 곳과 프로그램을 작성하는 곳이 멀리 떨어져 있지 않습니다. 짧은 문장을 입력하고, 그 문장에서 함수로, 함수에서 그림과 게임으로 나아갑니다.

이 책에서는 그 목표를 실습 원칙으로 옮겼습니다. 작은 예제, 전부 보이는 코드, 원본 API, 자기 손으로 하는 수정입니다. 마지막 작품에도 외부 라이브러리를 붙이지 않습니다.

읽고 생각하기: 멋진 프로그램 하나를 떠올리세요. 그 프로그램에서 가장 먼저 이해하고 싶은 동작을 한 문장으로 적으세요. 그 문장이 이번 공부의 출발점입니다.

사람을 기억하는방식

Terry A. Davis는 1969년에 태어나 2018년에 세상을 떠났습니다. 현재 보존 사이트는 그를 추모하고, 가족이 정신질환으로 인한 고통을 덜어 주는 단체를 도와 달라고 요청했다는 내용을 전합니다.

2014년 인터뷰에서 테리는 자신의 운영체제 안에서 직접 만든 컴파일러와 편집기로 대부분의 개발을 한다고 설명했습니다. 웹을 보고 영상을 만드는 작업에는 다른 운영체제와 도구도 사용했습니다. 작품에 대한 강한 신념과 일상적인 개발 작업이 함께 있었음을 알 수 있습니다.

그의 신앙은 이 프로젝트의 중요한 동기입니다. 책에서는 그가 믿고 기록한 바를 그에게 귀속해 설명합니다. 독자에게 같은 종교적 판단을 요구하지 않으며, 그의 작업을 이해하고 정성껏 이어 가는 태도를 제안합니다.

인터넷의 짧은 영상만으로 한 사람의 삶을 다 알 수는 없습니다. 질병이 천재성을 만들었다거나 코딩이 질병을 치료했다는 주장은 이 책의 근거로 삼지 않습니다. 비하 발언이나 고통스러운 순간을 학습의 재미로 소비하지도 않습니다.

이 책이 오래 바라볼 대상은 그가 남긴 작업입니다. 무엇을 만들었는지, 어떤 선택을 했는지, 우리가 무엇을 배우고 새로 만들 수 있는지에 집중합니다.

영상 설명을자료와 대조하기

전달된 설명 조사 뒤의 정리
문자 기반 화면이다 기본 화면은 VGA 640×480, 16색 그래픽 모드다. 글자도 그 화면에 그린다.
입력 즉시 실행된다 전역 문장을 실제 x86-64 기계어로 컴파일해 실행한다. 인터프리터라는 뜻은 아니다.
main이 없어도 된다 맞다. 함수 밖의 문장이 순서대로 실행된다.
커널과 사용자 프로그램의 경계가 없다 모두 ring 0에서 실행하고 하나의 주소 맵을 공유한다. 일반 OS의 격리와 다르다.
인터넷이 없어서 무조건 안전하다 네트워크 기능은 없다. 그러나 잘못된 메모리 접근이나 가져온 코드의 오류까지 막는 것은 아니다.
정확히 12만 줄이다 문서·시점·포함 범위에 따라 달라진다. 한 숫자를 영구적인 총량으로 고정하지 않는다.

성적, 유년기의 상세 일화, CIA 추적에 대한 경험담, 치료 변화와 사망의 의도는 본 강의의 확정 사실로 채택하지 않았습니다. 제공 대본의 시각표시는 조사 출발점이며 출처의 증명이 아닙니다.

작은 연구 습관: “누가 말했다”, “문서에 어떤 동작이 적혔다”, “내가 직접 실행했다”를 구별해 기록하세요. 같은 한 줄이라도 근거의 종류가 다릅니다.

02 · 준비

가상 컴퓨터를작업실로 쓰기

가상머신은 현재 컴퓨터 안에서 별도의 컴퓨터를 흉내 내는 프로그램입니다. TempleOS는 x86-64 PC를 대상으로 합니다. Apple Silicon Mac의 CPU와는 구조가 다르므로 x86-64 에뮬레이션을 사용합니다.

이 책의 기준 설정은 PC/i440FX, x86-64, BIOS, 메모리 512 MiB, CPU 1개, 표준 VGA, IDE 광학 드라이브입니다. 네트워크 장치는 추가하지 않습니다. 원본 문서의 최소 메모리는 512 MiB입니다.

공식 보존 사이트의 Downloads에서 TempleOS.ISO를 받습니다. ISO는 부팅용 디스크 이미지입니다. 이름이 비슷한 Lite판이나 후속 배포판을 먼저 고르지 마세요. 원본과 다른 부분이 있으면 책의 화면과 맞지 않을 수 있습니다.

처음에는 하드디스크 없이 ISO만 연결해 부팅합니다. 설치 여부를 물으면 n을 선택해 둘러볼 수 있습니다. 이 단계에서는 운영체제를 새로 설치할 필요가 없습니다.

작업 경계: 책의 실습 디스크는 새로 만든 이미지 파일입니다. 실제 컴퓨터의 디스크나 다른 업무용 VM의 디스크를 연결하지 않습니다. 이 원칙을 지키면 시행착오를 분리해 다룰 수 있습니다.

자료 출처: templeos.org/Downloads/의 원본 배포 이미지와 TempleOS의 Requirements 문서.

Mac·Windows·Linux의출발점

환경 시작 방법 확인할 항목
Apple Silicon Mac UTM의 Emulate 또는 QEMU의 TCG로 x86-64 선택 ARM 가상화가 아닌 x86-64 에뮬레이션
Intel Mac x86-64 QEMU 또는 호환 VM BIOS와 IDE, 표준 VGA
Windows PC x86-64를 지원하는 QEMU/VM 프로그램 ISO를 CD/DVD로 연결, UEFI 사용 해제
Linux PC QEMU의 PC 머신 같은 장치 구성으로 먼저 부팅

UTM에서는 새 VM을 만들 때 에뮬레이션을 선택하고 아키텍처를 x86_64로 지정합니다. 시스템은 Standard PC (i440FX + PIIX) 계열을 선택합니다. 설정 명칭은 앱 버전에 따라 조금 다를 수 있습니다.

이 책의 명령줄 경로는 QEMU가 이미 설치되어 있다고 가정합니다. 설치는 각 도구의 공식 배포 안내를 이용하세요. 명령을 찾을 수 없다는 오류는 TempleOS 문법 오류가 아니라 호스트 도구의 설치 또는 PATH 문제입니다.

호스트는 현재 사용 중인 Mac·Windows·Linux이고, 게스트는 가상머신 안의 TempleOS입니다. 다음 강의에서 이 두 곳의 명령을 구분합니다. Ed()를 Mac 터미널에 입력하거나 QEMU 명령을 TempleOS에 입력하지 않도록 주의하세요.

QEMU로첫 부팅

아래 명령은 호스트 터미널에서 실행합니다. TempleOS.ISO를 현재 폴더에 놓고 한 줄로 입력하세요. Windows PowerShell에서도 QEMU가 PATH에 등록되어 있으면 같은 한 줄을 사용할 수 있습니다.

qemu-system-x86_64 -machine pc -accel tcg -cpu qemu64 -m 512 -smp 1 -cdrom TempleOS.ISO -boot d -vga std -nic none

-machine pc는 오래된 PC 호환 장치를 구성합니다. -accel tcg는 CPU를 소프트웨어로 에뮬레이션합니다. -m 512는 게스트 메모리, -cdrom은 광학 디스크 이미지, -boot d는 CD 부팅을 뜻합니다.

-nic none은 가상 네트워크 장치를 만들지 않습니다. 이 명령에는 저장용 하드디스크가 없습니다. 설치 질문에 n을 입력하고, 화면을 구경한 뒤 종료해도 됩니다.

정상 징후: TempleOS V5.03, 파란 테두리의 창, 명령을 입력할 수 있는 커서가 보입니다. 화면의 글자가 작다면 VM 창 자체를 확대하세요. TempleOS의 원래 해상도를 바꾸는 과정은 아닙니다.

메모리·CPU·그래픽을 동시에 여러 개 바꾸지 마세요. 문제가 생기면 기준 설정으로 돌아온 뒤 한 가지씩 바꿉니다. 재현 가능한 출발점이 가장 좋은 디버깅 도구입니다.

VALUES.HC
TempleOS · 작업 폴더 / VALUES.HC
U0 Values()
{
  I64 candles=7;
  I64 rows=3;
  F64 length=2.5;
  "Candles: %d\n",candles;
  "Total: %d\n",candles*rows;
  "Length: %.2f\n",length;
}
Values;

이 파일의 바깥은 Values라는 함수를 정의합니다. 마지막 Values;가 그 함수를 호출합니다. 함수 문법은 뒤에서 자세히 배우므로 지금은 중괄호 안을 순서대로 읽어 보세요.

%d는 정수를 넣을 자리, %.2f는 소수점 아래 두 자리까지 표시할 자리입니다. 쉼표 뒤의 값이 그 자리를 채웁니다. 출력은 Candles: 7, Total: 21, Length: 2.50입니다.

04 · 값과 형

정수와 실수의차이

I64는 8바이트 부호 있는 정수, U8은 1바이트 부호 없는 정수, F64는 8바이트 부동소수점 수입니다. U0은 반환값이 없음을 나타낼 때 사용합니다. HolyC에는 기본 F32 형이 없습니다.

TYPES.HC
TempleOS · 작업 폴더 / TYPES.HC
U0 Types()
{
  I64 whole=7/2;
  F64 fraction=7.0/2.0;
  "I64 bytes: %d\n",sizeof(I64);
  "U8 bytes: %d\n",sizeof(U8);
  "Integer: %d\n",whole;
  "Fraction: %.1f\n",fraction;
  "Remainder: %d\n",7%2;
}
Types;

정수끼리 나눈 7/2의 결과는 3입니다. 소수 부분이 자동으로 보관되지 않습니다. 7.0/2.0은 실수 계산이므로 3.5가 됩니다. %는 나머지이므로 7%2는 1입니다.

바이트는 저장 공간의 단위입니다. sizeof로 형의 크기를 확인할 수 있습니다. 변수의 값과 변수가 차지하는 크기를 혼동하지 마세요. 7을 담은 I64도 8바이트입니다.

해 보기: 10을 3으로 나눈 몫과 나머지를 예상한 뒤 출력하세요. 소수 결과가 필요하면 어느 피연산자를 바꿔야 할지도 적어 보세요.

조건은 참 또는 거짓으로 판단하는 식입니다. lamps>0이 참이면 첫 번째 중괄호 안으로 들어갑니다. 거짓이면 else 쪽을 실행합니다. 들여쓰기는 사람이 구조를 읽기 좋게 도와줍니다.

CHOICE.HC
TempleOS · 작업 폴더 / CHOICE.HC
U0 Choice()
{
  I64 lamps=3;
  if (lamps>0) {
    "The room has light.\n";
  } else {
    "Light a lamp.\n";
  }
  if (1<=lamps<=7)
    "Between one and seven.\n";
}
Choice;

HolyC는 1<=lamps<=7 같은 연속 비교를 지원합니다. 여기서는 lamps가 1 이상 7 이하일 때 참입니다. 이 문법을 표준 C에 그대로 옮기면 같은 뜻이 되지 않습니다.

기록표 만들기: lamps에 0, 3, 8을 넣었을 때 첫 조건과 둘째 조건이 각각 참인지 써 보세요. 프로그램의 출력과 일치하는지 확인합니다.

함수는 입력을 받아 일을 하고, 필요하면 결과를 돌려주는 묶음입니다. Square는 정수 n을 받아 제곱을 반환합니다. Greet는 문장을 출력하므로 반환 형이 U0입니다.

FUNCS.HC
TempleOS · 작업 폴더 / FUNCS.HC
I64 Square(I64 n)
{
  return n*n;
}
U0 Greet(U8 *name="friend")
{
  "Peace, %s.\n",name;
}
Greet;
Greet("Terry");
"Square: %d\n",Square(4);

Greet의 name에는 기본값이 있습니다. 인수를 생략하면 friend를 사용하고, Greet("Terry")처럼 값을 주면 그 값을 사용합니다. 인수가 없거나 기본값만 사용하면 괄호를 생략할 수 있습니다.

07 · 함수

이름이 살아 있는범위

함수 안에서 만든 변수는 그 함수를 읽는 동안 이해할 수 있는 작은 범위를 갖습니다. 앞의 Values에서 만든 candles를 다른 함수에서 마음대로 사용할 수는 없습니다. 필요한 값은 인수로 전달하는 방법부터 익히세요.

함수 밖의 전역 변수는 여러 함수가 함께 볼 수 있습니다. 움직이는 그림의 위치처럼 여러 동작이 공유해야 하는 상태에 사용합니다. 그러나 모든 값을 전역으로 만들면 어느 함수가 바꿨는지 추적하기 어려워집니다.

TempleOS의 작업에는 컴파일러의 심볼 표와 메모리가 있습니다. 명령줄에서 정의한 함수는 그 작업에서 계속 호출할 수 있습니다. 파일을 반복해서 포함하면 새 코드용 메모리가 쌓일 수도 있습니다.

정리 방법: 실습이 끝난 터미널 작업을 닫고 새 작업에서 같은 파일을 실행합니다. 이전의 정의나 값에 기대지 않고도 실행되는지 확인하는 과정입니다. 운영체제 전체를 재설치할 이유는 없습니다.

작은 설계 질문: 이 변수는 함수 한 곳에서만 필요한가, 여러 함수가 함께 쓰는가? 이 값을 바꿀 책임은 어디에 있는가? 이 두 질문에 답할 수 있으면 이름의 범위를 선택하기 쉬워집니다.

마지막 작품에서는 켜진 등불을 나타내는 정수 하나를 전역으로 두고, 입력 함수가 바꾸며 그리기 함수가 읽습니다. 역할이 분명한 공유 상태의 예입니다.

08 · 배열

여러 상자를나란히 놓기

배열은 같은 형의 값을 나란히 보관합니다. count[4]는 정수 네 개를 위한 자리입니다. 첫 번째 위치의 번호는 0이고, 마지막은 3입니다. 네 개짜리 배열의 count[4]는 범위를 벗어납니다.

ARRAYS.HC
TempleOS · 작업 폴더 / ARRAYS.HC
U0 Seeds()
{
  I64 count[4];
  count[0]=2;
  count[1]=3;
  count[2]=5;
  count[3]=7;
  I64 i,total=0;
  for (i=0;i<4;i++) {
    "Bed %d: %d\n",i,count[i];
    total+=count[i];
  }
  "All seeds: %d\n",total;
}
Seeds;

함수 안의 배열은 먼저 선언하고 각 칸에 값을 넣습니다. 반복 조건이 i<4인 이유를 말해 보세요. 0, 1, 2, 3이라는 네 인덱스를 차례로 방문합니다. 합계는 17입니다.

TempleOS가 배열의 범위를 자동으로 보호한다고 생각하면 안 됩니다. 범위를 넘으면 다른 메모리를 읽거나 바꿀 수 있습니다. 인덱스와 길이를 종이에 같이 적는 습관이 도움이 됩니다.

해 보기: 다섯 번째 값을 추가하려면 선언의 길이와 반복 조건을 함께 바꿔야 합니다. 한 곳만 바꾸면 어떤 문제가 생길지 먼저 설명하세요.

08 · 문자열

문자도배열 안에 있다

ASCII 문자열은 문자 바이트들이 이어진 배열입니다. 끝에는 값이 0인 종료 문자가 있습니다. 화면의 숫자 0과 문자열을 끝내는 0바이트는 서로 다릅니다.

STRINGS.HC
TempleOS · 작업 폴더 / STRINGS.HC
U0 Words()
{
  U8 text[16];
  StrCpy(text,"PEACE");
  "Before: %s\n",text;
  "Length: %d\n",StrLen(text);
  "First: %c\n",text[0];
  text[0]='p';
  "After: %s\n",text;
}
Words;

text[16]은 16바이트를 마련합니다. StrCpy로 PEACE와 종료 문자를 그 안에 복사합니다. 함수 안에서는 이처럼 공간 선언과 값 넣기를 나누어 씁니다. StrLen은 종료 문자 전까지의 길이인 5를 돌려줍니다. %c는 문자 하나, %s는 문자열을 표시합니다. 첫 바이트를 소문자 p로 바꾼 뒤에는 pEACE가 나옵니다.

예제는 쓰기 가능한 배열을 선언합니다. 문자열 리터럴을 가리키는 포인터와 배열은 같은 물건이 아닙니다. 수정할 문자열의 저장 공간을 어떻게 확보했는지 확인하세요.

한 곳 바꾸기: text[0]='G';로 고치면 GEACE가 됩니다. 예쁜 단어를 만들기보다 첫 번째 바이트를 바꿨다는 사실을 확인하는 연습입니다.

확인: 문자열 길이 15인 내용을 담으려면 종료 문자를 포함해 최소 몇 바이트가 필요할까요? 답은 16바이트입니다.

09 · 주소

값의 자리로찾아가기

변수는 값을 담고, 주소는 그 변수가 어디 있는지 나타냅니다. 포인터는 그 주소를 보관합니다. &lamp는 lamp의 주소를 구하고, *address는 그 주소가 가리키는 값을 읽거나 씁니다.

POINTER.HC
TempleOS · 작업 폴더 / POINTER.HC
U0 PointerLesson()
{
  I64 lamp=3;
  I64 *address=&lamp;
  "Before: %d\n",lamp;
  *address=7;
  "After: %d\n",lamp;
}
PointerLesson;

처음 출력은 3, 다음 출력은 7입니다. 포인터에 새 주소를 넣은 것이 아니라, 포인터가 가리키는 자리의 내용을 바꿨기 때문입니다.

I64 *address를 “I64 값을 가리키는 포인터 address”라고 읽으세요. 선언의 별표와 식에서 값을 꺼낼 때의 별표는 등장 위치에 따라 역할이 다릅니다.

그림으로 설명하기: 종이에 lamp 상자를 그리고 3을 적습니다. address 상자에서 lamp로 화살표를 연결합니다. 별표 대입이 실행될 때 어느 상자의 내용이 바뀌는지 표시하세요.

주소를 임의의 숫자로 만들어 접근하는 연습은 하지 않습니다. 먼저 자신이 선언한 변수의 주소만 이용해 관계를 이해합니다.

09 · 주소 지도

같은 자리를다른 이름으로

다음은 POINTER.HC의 관계를 그린 개념도입니다. 상자의 위치는 실제 메모리 주소가 아닙니다. 주소를 담은 포인터와 그 주소가 가리키는 값을 구별하기 위한 그림입니다.

address&lamp
가리킨다 →
lamp3

*address = 7;

address&lamp
가리킨다 →
lamp7
위치 관계는 같고, 가리킨 자리의 값이 바뀝니다.

첫 장면에서 lamp에는 3이 있습니다. address에는 lamp의 위치가 들어 있습니다. 화살표는 값이 복사되었다는 뜻이 아니라, 어느 자리로 찾아갈지를 뜻합니다.

두 번째 장면에서 *address=7을 실행합니다. 바뀌는 것은 lamp의 내용입니다. address가 가리키는 대상은 여전히 lamp입니다. 이후 lamp를 출력해도, *address를 출력해도 7을 읽습니다.

직접 그리기: lamp2를 새로 선언하고 address가 lamp2를 가리키도록 바꾼다면 화살표가 어떻게 달라질까요? 새로운 주소를 넣는 일과 주소 안의 값을 바꾸는 일을 그림으로 나눠 보세요.

포인터가 어려울 때는 문장만 반복해서 읽기보다 이름, 값, 화살표를 종이에 그립니다. 한 번에 변수 두 개 정도로 시작하면 관계를 놓치지 않습니다.

09 · 레코드

함께 다닐 값을한데 묶기

등불 하나에는 위치 x, 위치 y, 켜짐 여부가 필요합니다. 서로 관련된 값을 하나의 레코드로 묶으면 프로그램의 뜻이 잘 보입니다. HolyC의 class를 여기서는 구조체처럼 사용합니다.

RECORD.HC
TempleOS · 작업 폴더 / RECORD.HC
class CLamp
{
  I64 x,y;
  Bool lit;
};
U0 RecordLesson()
{
  CLamp lamp;
  lamp.x=120;
  lamp.y=80;
  lamp.lit=TRUE;
  "Lamp: %d,%d lit=%d\n",
    lamp.x,lamp.y,lamp.lit;

RecordLesson;

lamp.x처럼 점을 사용해 멤버를 선택합니다. Bool은 참·거짓을 표현하며, TRUE와 FALSE를 사용할 수 있습니다. 출력은 Lamp: 120,80 lit=1입니다.

HolyC의 class를 C++의 접근 제한이나 객체 수명 관리까지 갖춘 것처럼 생각하지 마세요. 이 책은 데이터 묶음으로서의 역할을 먼저 익힙니다. 포인터로 가리킨 레코드에서는 ptr->x처럼 화살표를 씁니다.

해 보기: 등불을 하나 더 선언해 다른 위치와 꺼진 상태를 넣습니다. 같은 형을 사용해 두 개의 독립된 값을 만들었다는 점을 확인하세요.

09 · 메모리

빌린 자리는돌려주기

프로그램이 실행되는 동안 필요한 공간을 요청할 수도 있습니다. MAlloc은 지정한 바이트 수만큼 메모리를 마련하고 주소를 돌려줍니다. 사용을 끝내면 Free로 반환합니다.

HEAP.HC
TempleOS · 작업 폴더 / HEAP.HC
U0 HeapLesson()
{
  I64 i;
  I64 *values=MAlloc(4*sizeof(I64));
  if (!values)
    return;
  for (i=0;i<4;i++)
    values[i]=i*i;
  "Last: %d\n",values[3];
  Free(values);
  values=NULL;
}
HeapLesson;

필요한 공간은 정수 네 개이므로 4*sizeof(I64)입니다. 4바이트가 아닙니다. 포인터가 유효한지 확인하고 네 값을 쓴 뒤 마지막 값 9를 출력합니다.

Free 뒤에는 그 주소로 다시 읽거나 쓰지 않습니다. values=NULL은 손에 남아 있는 포인터를 비워 잘못된 재사용을 줄이는 표시입니다. 이미 반환한 공간을 또 반환하는 것도 오류입니다.

정리 규칙: 확보한 곳, 사용한 곳, 반환한 곳을 한 줄씩 짚어 보세요. 중간에 return을 추가하면 반환을 건너뛰는 경로가 생기는지도 살핍니다.

10 · 기록

작은 메모를파일에 쓰기

메모리는 작업이 끝나면 사라질 수 있습니다. 파일은 저장 장치에 내용을 남기는 방법입니다. 저장 가능한 실습 폴더에서 실행하세요. 이 예제는 그 폴더의 NOTE.TXT를 새 내용으로 씁니다.

SAVE.HC
TempleOS · 작업 폴더 / SAVE.HC
U0 SaveNote()
{
  U8 *text="A small work, made with care.\n";
  I64 size=StrLen(text);
  FileWrite("NOTE.TXT",text,size);
  "Requested bytes: %d\n",size;
}
SaveNote;

FileWrite는 파일명, 바이트들의 주소, 쓸 바이트 수를 받습니다. StrLen(text)는 문장과 줄바꿈의 길이를 계산합니다. 문자열 종료용 0바이트는 텍스트 파일의 본문에 쓰지 않습니다.

예상 출력은 Requested bytes: 30입니다. 이것은 쓰도록 요청한 길이입니다. FileWrite의 반환값은 기록한 바이트 수가 아니므로 길이 확인에 쓰지 않습니다. 실제 저장은 다음 예제에서 읽은 길이와 내용으로 확인합니다.

같은 파일명으로 다시 실행하면 메모 내용이 바뀝니다. 소중한 파일명을 실습 대상으로 쓰지 마세요. 처음에는 책의 전용 실습 폴더에만 기록합니다.

해 보기: 문장을 짧게 바꾸고 요청한 길이와 다시 읽은 길이가 어떻게 달라지는지 확인하세요. 글자 수와 바이트 수가 같은 것은 이 예제가 ASCII만 사용하기 때문입니다.

10 · 기록

저장한 내용을다시 읽기

파일을 읽으면 내용이 들어 있는 메모리의 주소와 길이를 얻습니다. 파일에 문자열 종료 문자가 있다고 가정하지 않고, 받은 길이만큼 정확히 출력해 봅니다.

READ.HC
TempleOS · 작업 폴더 / READ.HC
U0 ReadNote()
{
  I64 size=0,i;
  U8 *text=FileRead("NOTE.TXT",&size);
  if (!text) {
    "Run SAVE.HC first.\n";
    return;
  }
  "Read bytes: %d\n",size;
  for (i=0;i<size;i++)
    "%c",text[i];
  Free(text);
}
ReadNote;

&size를 넘겼기 때문에 FileRead가 읽은 크기를 size에 써 줄 수 있습니다. 앞에서 배운 주소 전달이 실제 API에서 쓰이는 예입니다. Read bytes: 30과 원래 문장이 나오는지 확인합니다. 성공했다면 마지막에 Free(text)로 받은 버퍼를 반환합니다.

순서: SAVE.HC 실행 → Dir로 파일 확인 → READ.HC 실행 → 원래 문장과 비교. 새 터미널에서도 같은 폴더로 이동해 읽을 수 있는지 확인합니다.

파일이 없는 경우와 빈 파일은 다릅니다. 이 입문 예제는 존재하는 비어 있지 않은 NOTE.TXT를 정상 경로로 사용합니다. 더 큰 프로그램에서는 실패와 길이가 0인 결과를 구분해 처리하세요.

10 · 입력

사용자의 말을받아 보기

프로그램이 미리 정해 둔 문장만 출력한다면 대화가 이어지지 않습니다. GetStr은 입력을 기다리고 사용자가 쓴 문자열을 돌려줍니다. Enter로 입력을 마칩니다.

INPUT.HC
TempleOS · 작업 폴더 / INPUT.HC
U0 SayHello()
{
  U8 *name=GetStr("Your name: ");
  if (name) {
    "Hello, %s.\n",name;
    Free(name);
  }
}
SayHello;

Your name:이 나오면 영문 이름을 입력하세요. 입력한 이름이 인사말에 들어갑니다. 받은 문자열은 동적으로 확보된 공간이므로 사용 후 Free로 반환합니다.

여기서 %s는 문자열을 넣을 자리입니다. 사용자 입력 자체를 형식 문자열로 실행하지 않고, 고정된 형식에 데이터로 넣는 구조를 유지하세요.

해 보기: 짧은 이름, 공백이 있는 두 단어, 빈 입력을 차례로 시험하세요. 어떤 화면이 나오는지 적습니다. 입력 경로에서 조작하기 쉬운 작은 차이를 먼저 확인하는 것이 좋은 테스트입니다.

예측하지 못한수를 만들기

난수는 프로그램에 여러 선택을 주는 도구입니다. 이번에는 1에서 6 사이의 수를 여섯 번 출력합니다. RandU32가 준 수를 6으로 나눈 나머지는 0부터 5 사이이므로 1을 더합니다.

DICE.HC
TempleOS · 작업 폴더 / DICE.HC

{

  for (i=0;i<6;i++) {
    value=1+RandU32%6;
    "%d\n",value;
  }
}
SixNumbers;

예상 결과는 특정 숫자열이 아닙니다. 여섯 줄이며 각 값이 1 이상 6 이하인지를 확인합니다. 우연히 같은 숫자가 연속으로 나와도 곧바로 오류는 아닙니다.

나머지를 사용하는 간단한 방식에는 분포의 아주 작은 편향이 생길 수 있습니다. 이 예제는 범위와 관찰을 배우는 데 목적이 있으며, 추첨·보안용 난수의 품질을 보증하지 않습니다.

테리는 무작위 선택과 성경 구절을 자신의 종교적 작업에 연결했습니다. 이 책은 프로그램이 어떤 선택을 했는지와 그 선택에 사람이 부여하는 의미를 구별해 읽습니다. 난수의 출력이 무엇을 말하는지 대신 단정하지 않습니다.

640×480 안에서길 찾기

화면의 왼쪽 위를 원점으로 생각하세요. x는 오른쪽으로 갈수록, y는 아래로 갈수록 커집니다. 원본 전체 화면에는 가로 640, 세로 480개의 픽셀 자리가 있습니다.

창 안에 그릴 때는 창의 실제 그리기 영역을 기준으로 생각해야 합니다. 640×480이라는 숫자를 모든 창의 크기로 가정하지 마세요. 창이 둘로 나뉘어 있으면 한 창의 폭은 훨씬 작습니다.

CDC는 그리기에 필요한 설정과 대상을 담는 구조입니다. 색을 정하고 좌표를 넘겨 도형을 그립니다. DCAlias는 현재 작업의 화면에 그릴 수 있는 컨텍스트를 얻는 데 사용합니다.

함수 뜻 주의할 인수
GrRect 채운 사각형 x, y, 폭, 높이

U0 PaletteLesson()

13 · 조작

키로작은 순례자 움직이기

키 입력을 상태 변화에 연결합니다. 영문 소문자 a와 d로 이동하고 q로 끝냅니다. Shift를 누른 대문자 입력은 별도로 처리하지 않은 예제입니다.

MOVE.HC
TempleOS · 작업 폴더 / MOVE.HC
I64 pilgrim_x=100;
U0 PilgrimDraw(CTask *,CDC *dc)
{
  dc->color=BLUE;
  GrRect(dc,pilgrim_x,100,12,12);
}
U0 Pilgrim()
{
  I64 key;
  SettingsPush;
  DocClear;
  Fs->draw_it=&PilgrimDraw;
  "A/D: move, Q: finish\n";
  while ((key=GetChar(,FALSE))!='q') {
    if (key=='a') pilgrim_x-=8;
    if (key=='d') pilgrim_x+=8;
    pilgrim_x=ClampI64(pilgrim_x,8,240);
  }
  SettingsPop;
}
Pilgrim;

GetChar(,FALSE)는 첫 인수를 기본값으로 두고, 두 번째 인수에서 입력 글자의 자동 출력을 끕니다. 기본 인수 사이의 생략을 허용하는 HolyC 문법입니다.

TempleOS의 기본 소리는 PC 스피커와 관련된 단순한 구조입니다. 여러 음을 한꺼번에 쌓는 현대 오디오 작업과 다른 제약이 있습니다. 여기서는 음을 내고, 잠깐 기다리고, 끄는 순서를 배웁니다.

U0 ThreeTones()
{

15 · DolDoc

글 안에기능이 들어 있는 문서

DolDoc는 TempleOS의 문서 형식입니다. 단순한 텍스트에 색, 링크, 위젯, 그래픽 자원을 연결합니다. 명령줄·편집기·도움말이 같은 문서 체계를 공유하므로 코드에서 문서로 이동하기 쉽습니다.

DOC.HC
TempleOS · 작업 폴더 / DOC.HC
U0 Letter()
{
  "$$FG,BLUE$$A SMALL OFFERING$$FG$$\n";
  "Make something with care.\n";
  "$$UL,1$$Read. Change. Share.$$UL,0$$\n";
}
Letter;

소스의 $$는 DolDoc 제어 구문을 출력할 때 사용하는 이스케이프입니다. FG는 글자색, UL은 밑줄을 제어합니다. 뒤에서 색과 밑줄을 되돌리는 부분도 함께 읽으세요.

관찰하기: 첫 줄만 색이 바뀌는지, 밑줄이 마지막 문장에만 적용되는지 확인합니다. 서식을 시작했으면 끝내는 코드까지 짝지어 읽습니다.

문서의 겉모습과 내부 명령을 번갈아 보면 이해하기 쉽습니다. Ctrl+T는 일반 텍스트 보기 전환에 쓰입니다. 글자가 깨진 것처럼 보여도 제어 구문을 표시하는 상태인지 먼저 확인하세요.

16 · 컴파일러

문장에서기계어까지

컴퓨터는 HolyC의 단어를 그대로 실행하지 않습니다. 컴파일러가 문법을 읽고 기계어를 만들어 메모리에 둡니다. 명령줄에서 바로 반응한다고 해서 해석기라는 뜻은 아닙니다.

입력한 코드 → 문법 분석 → 기계어 생성 → 메모리에 배치 → 실행의 흐름을 생각하세요. 이 책은 컴파일러 자체를 새로 구현하지 않지만, 실행 모델을 알고 코드를 읽는 것은 중요합니다.

TempleOS에서는 함수 밖의 문장이 실행됩니다. 함수 정의는 동작에 이름을 붙이는 단계이고, 마지막의 함수 호출이 실제 작업을 시작합니다. 파일을 열었다는 사실과 함수를 실행했다는 사실을 구분하세요.

JIT는 실행할 때 메모리에서 쓸 코드를 컴파일하는 방식입니다. AOT는 미리 바이너리 파일을 만드는 경로입니다. TempleOS는 두 방식이 있으며, 일반적인 실습은 #include를 통한 JIT 경로를 이용합니다.

확인 과제: FUNCS.HC에서 마지막 세 호출을 잠시 지우고 포함해 보세요. 함수는 정의되지만 예상한 인사말은 출력되지 않습니다. 이어서 명령줄에서 Greet를 호출하면 어떻게 될지 예상하세요.

컴파일러의 원본 길잡이는 Doc/CompilerOverview.DD와 Compiler 폴더입니다. 입문 단계에서는 “무엇이 언제 실행되는가”를 설명할 수 있으면 충분합니다.

16 · 메모리

하나의 넓은작업 공간

일반적인 운영체제는 사용자 프로그램과 커널의 권한을 나누고 서로의 메모리를 보호합니다. TempleOS는 모두 ring 0에서 실행하며 하나의 주소 맵을 공유합니다. 테리는 직접 접근할 수 있는 단순함을 선택했습니다.

이 덕분에 프로그램에서 운영체제의 함수와 자료에 가까이 접근할 수 있습니다. 반대로 잘못 쓴 포인터 하나가 넓은 범위의 동작을 망가뜨릴 수 있습니다. “내 프로그램만 종료될 것”이라고 가정하지 마세요.

설계의 교환: 접근의 자유와 이해하기 쉬운 구조를 얻는 대신, 격리와 보호가 주는 장점을 줄입니다. 이것을 모든 컴퓨터에 적용할 정답이라고 일반화할 필요는 없습니다. TempleOS의 목적과 함께 평가합니다.

책의 포인터 예제는 자신이 선언하거나 확보한 공간만 다룹니다. 커널의 임의 주소에 수를 쓰는 실습으로 시작하지 않습니다. 읽기부터 시작해 함수 선언, 인수, 호출자를 확인하세요.

설명하기: 주소를 공유한다는 것과 네트워크가 없다는 것은 다른 축의 설계입니다. 두 특징을 각각 한 문장으로 적습니다. 외부 연결이 없다는 사실이 모든 종류의 오류를 없애 주지는 않습니다.

16 · 작업

기다리는 동안다른 일이 진행되기

작업은 실행 상태와 메모리 등을 가진 단위입니다. TempleOS의 기본 스케줄링은 협력적인 방식입니다. 오래 걸리는 반복문에서는 다른 작업이 진행할 기회를 주는 일이 중요합니다.

TASKS.HC
TempleOS · 작업 폴더 / TASKS.HC
U0 CountSlowly()
{
  I64 i;
  for (i=1;i<=5;i++) {
    "Count %d\n",i;
    Sleep(250);
  }
}
CountSlowly;

숫자 다섯 개가 약 250밀리초 간격으로 나옵니다. Sleep은 노트북의 절전 기능이 아닙니다. 현재 작업이 일정 시간 기다리도록 하는 호출입니다.

Yield는 다음 작업으로 실행 기회를 넘기는 데 쓰입니다. 기다리는 반복문에서 Sleep이나 Yield를 없애면 다른 작업의 반응과 CPU 사용이 달라질 수 있습니다. 무한 반복을 만들어 버리기보다 유한한 횟수로 비교하세요.

관찰하기: 프로그램이 출력하는 동안 다른 창의 변화가 보이는지 확인합니다. 코드가 짧아도 화면의 여러 일이 동시에 진행되는 듯 보이는 원리를 생각해 봅니다.

사용 규칙

  • 1~7: 해당 등불을 켜거나 끈다.
  • r: 모든 등불을 끈다.
  • q: 설정을 복구하고 끝낸다.

제작 규칙

  • 원본 TempleOS의 함수만 사용한다.
  • 다른 파일이나 외부 라이브러리 없이 한 파일로 실행한다.

  • 처음 사용하는 사람에게 조작과 종료 방법을 알려 준다.

앞에서 배운 배열·포인터가 모두 필요한 것은 아닙니다. 이번 상태는 일곱 개의 비트로 충분히 표현됩니다. 배운 기능을 전부 넣기보다 필요한 것을 선택하는 연습입니다.

일곱 상태를한 수에 담기

정수의 이진수 자릿수 하나는 켜짐·꺼짐을 표현할 수 있습니다. 가장 오른쪽 자리부터 첫 번째 등불에 대응시킵니다. 첫 등불의 마스크는 1, 둘째는 2, 셋째는 4입니다.

등불 마스크 만들어 내는 식
1 1 1<<0
2 2 1<<1
3 4 1<<2
7 64 1<<6

1부터 10까지 합은 55입니다. 시작 값을 0으로 바꾸고 끝을 10으로 유지하면 출력은 11줄이지만 합은 여전히 55입니다. 반복 횟수와 합계가 서로 다른 결과라는 점을 봅니다.

07장 · 함수 만들기

I64 Add(I64 a,I64 b)
{
  return a+b;
}
"%d
",Add(2,5);

결과는 7입니다. 출력은 함수 밖에서 하므로 함수의 반환값을 다른 계산에 넣을 수도 있습니다. Add가 인사를 출력하는 등 다른 일을 하도록 섞지 않습니다.

연습 문제해설 2

08장 · 다섯 칸 배열

배열 길이를 5로 바꾸고 값 다섯 개를 초기화합니다. 반복 조건은 i<5가 됩니다. i<=5이면 여섯 번째 위치까지 접근하므로 범위를 벗어납니다.

09장 · 주소

*address=7은 lamp 상자의 내용을 바꿉니다. address가 가리키는 대상은 바뀌지 않았습니다. 주소를 바꾸는 대입과 그 주소의 값을 바꾸는 대입을 구분합니다.

12장 · 움직임

i*3을 i*2로 바꾸면 반복 횟수는 60회 그대로이고 이동 간격이 줄어듭니다. Sleep만 늘리면 기다리는 시간이 길어집니다. 두 수정을 한 번에 하지 않아야 원인을 비교하기 쉽습니다.

18장 · 모두 켜기

입력 처리에 if (key=='f') garden_lit=127;을 추가할 수 있습니다. 화면 안내도 함께 바꾸고 r과 q가 그대로 동작하는지 확인합니다.

18장 · 다섯 등불

등불 수는 5, 허용 키는 1~5, 모두 켜진 상태는 31입니다. 더 일반적으로는 개수가 충분히 작은 정수일 때 (1<<count)-1로 마스크를 구할 수 있습니다. 형의 비트 수를 넘기는 시프트는 피합니다.
